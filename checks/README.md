## Порядок запуска

После интеграции коммитов D и подключения ETL B владельцем A:

```bash
bash scripts/build.sh
bash scripts/check.sh
```

`check.sh` сам запускает каждый файл отдельным psql с `BEGIN`, `ROLLBACK`,
`-X -q -v ON_ERROR_STOP=1`; SQL D не управляет транзакцией. Нарушение обязательного
инварианта вызывает `RAISE EXCEPTION`, runner возвращает ненулевой код при любой
ошибке файла. По контракту A runner собирает ошибки всех файлов, а не останавливается
на первом файле. Только полностью завершённый runner считается результатом приёмки.
Без ETL построятся пустые таблицы: сверки источников и календарь должны упасть.

| Файл / каталог | Назначение |
|---|---|
| `00_synthetic.sql` | Fanout, несколько платежей/отзывов, NULL, unknown, пустой месяц, повторный покупатель, чек, рассрочка; тест самого assert |
| `10_catalog.sql` | PostgreSQL 16, схемы, 10 таблиц core, валидированные ограничения; mart может пока быть пуст |
| `20_keys_and_types.sql` | NULL/дубли ключей, 7 FK, numeric без typmod, timestamp без timezone, текстовые индексы адреса |
| `30_source_reconciliation.sql` | Происхождение/кратность отказов; двусторонний EXCEPT ALL всех бизнес-полей raw минус rejects против core; адреса заказа, люди, повторные, категории |
| `40_join_and_money.sql` | Конечные неотрицательные деньги, сохранение строк/сумм при JOIN измерений и предагрегированных фактов, суммы продавцов/категорий |
| `50_calendar.sql` | Все дни без дыр, поля календаря, точные границы, месячная ось с нулевыми месяцами |
| `anomalies/*.sql` | Только SELECT: даты/позиции/платежи, рассрочка=0, пробелы отзывов, платёж против чека, категории, карантин |
| `lib/*.sql` | Подключаемые части; runner не запускает отдельно |
| `baseline/*.sql` | Отдельная приёмка фиксированной поставки; не ограничения будущих загрузок |
| `tools/snapshot.sql` | Отдельный снимок для воспроизводимости; не обязательный assert |

`assert_true` отвергает FALSE и NULL; `assert_numeric` сравнивает точно,
NULL = NULL только для проверки одинаково отсутствующих сумм. Округления нет,
кроме ожидаемого отображения в синтетике среднего чека. Отчёты выводят агрегаты
и не более пяти идентификаторов на тип аномалии, без текстов отзывов и адресов.

## Уточнения пользователя для A/B

- `etl_rejects.payload` — исходная строка целиком, **включая `_source_file`, `_loaded_at`**.
  `source_table` — имя без `raw.`, `reason` непустой. Одна отклонённая копия — одна
  строка карантина, несколько причин должны быть упакованы в неё. Каждый payload
  обязан существовать в raw с достаточной кратностью. Source_key не используется
  как доказательство: формата ключа v0 не определяет.
- Календарь: от начала месяца минимального оформления до конца месяца максимума
  **всех дат заказов**, включая обещанную доставку. Верхняя граница не только purchase.
- `review_comment_title` и `review_comment_message` сохраняются **точно как в raw**,
  включая краевые и полностью пробельные тексты. Для этих двух полей btrim/NULLIF
  не применяется; исходный NULL остаётся NULL. Решение принято по фактам профиля B.

Все три уточнения подтверждены пользователем в чате D 2026-10-28; контракт правит A.
Проверка 30 вычитает rejects через EXCEPT ALL, затем независимо приводит значения
по v0: btrim, пустая строка → NULL, явные типы, с исключением для текстов отзывов;
сравнивает в обе стороны с кратностью.
Преобразование estimated_delivery_date проверяется как timestamp против core date,
поэтому ненулевое исходное время нельзя незаметно отбросить. Категории — объединение
принятых переводов и непустых категорий принятых товаров. NULL не превращается в
выдуманную категорию core. Выбор причины отказа по бизнес-смыслу сверяется с профилем B
отдельно: совпадение payload само по себе не доказывает обоснованность изоляции.

Профиль B содержит аномалии хронологии, заказы без позиций/платежа и расхождения
payment_value против price+freight_value. Они не являются ошибками модели:
обязательны сохранность исходных значений и отсутствие размножения, а не равенство
платежа чеку или искусственная коррекция дат. Отчёт 20 показывает сопоставимую
популяцию и отсутствие дочерних наборов отдельно, сохраняя NULL.

## Baseline и воспроизводимость

В выделенной БД D с существующим raw. Compose v0 содержит фиксированные имя
контейнера/порт: отдельное окружение согласует A. `setup.sh --reset` не использовать.
Baseline проверяет DDL, filename, время загрузки и объёмы восьми таблиц раздатки
`3da32d149bfa14dca3fdb0c5863d0771c38efbfc`, всего 550 759 строк:

```bash
docker compose exec -T -w /work postgres psql -X -q -v ON_ERROR_STOP=1 -U hack -d marketplace \
  -c 'BEGIN ISOLATION LEVEL REPEATABLE READ' -f checks/baseline/01_raw_baseline.sql -c 'ROLLBACK'
```

Snapshot включает все колонки raw/core/mart, сохраняет кратность и игнорирует порядок.
В v0 технических timestamps core/mart нет; список исключений сейчас пуст. Исключать
бизнес-хронологию нельзя. При добавлении технических полей D указывает их явно.

```bash
set -e
snapshot() {
  docker compose exec -T -w /work postgres psql -X -q -v ON_ERROR_STOP=1 --csv -U hack -d marketplace \
    -c 'BEGIN ISOLATION LEVEL REPEATABLE READ' -f checks/tools/snapshot.sql -c 'ROLLBACK'
}
snapshot > checks/before.csv
bash scripts/build.sh
bash scripts/check.sh
snapshot > checks/first.csv
bash scripts/build.sh
bash scripts/check.sh
snapshot > checks/second.csv
git diff --no-index --exit-code checks/first.csv checks/second.csv
```

Это будущие команды, не протокол выполненного запуска. Перенаправление — на хосте:
`/work` смонтирован read-only. Остановиться при любом ненулевом коде build/check/psql.
Кроме полного совпадения first/second отдельно сравнить все строки schema_name=raw
между before/first/second. До первой сборки core/mart могут отсутствовать/отличаться.
Fingerprint — MD5 отсортированного мультимножества хешей JSONB-строк плюс row_count;
это детектор изменений, не криптографическое доказательство. Расхождения разбирать
по ключам/значениям; не убирать колонки ради совпадения. Сортировка требует ресурсов.
