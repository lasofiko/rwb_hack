# Развитие модели

Предложение D: текущий raw — 550 759 строк по профилю B; SLA ещё не измерен. MVP — PostgreSQL 16,
неизменяемый raw, core и витрины; сначала закончить корректность и повторяемость.

| Этап | Изменение и польза | Приёмка / риск |
|---|---|---|
| 1. Повторяемый batch | Реестр batch_id, источник, хеш файла, время загрузки; lineage и карантин с причинами | Повторная загрузка не удваивает строки; сверяется баланс. Риск нестабильного ключа источника |
| 2. История | Снимки/события статусов заказов, история изменяемых атрибутов товара и продавца с valid_from/valid_to; адрес заказа сохраняется | Нет пересечений интервалов, корректный as-of JOIN. Нынешний snapshot не позволяет восстановить прошлые переходы; историю не выдумывать |
| 3. Новые сущности | Возвраты/отмены на уровне позиций, возвраты платежей, комиссии и логистика отдельными фактами | Выручка, оборот, оплачено и возврат различаются; сверки с первичными источниками. Риск двойного учёта компенсаций |
| 4. Рост нагрузки | Индексы по измеренным планам, ANALYZE, предагрегации/материализация; инкремент с окном поздних данных; партиции только при пользе | Сверка инкремента с полным rebuild, EXPLAIN (ANALYZE, BUFFERS), блокировки/IO/время. Риск пропуска поздних исправлений |
| 5. Архитектурное расширение | Реплика для аналитики, затем отдельное хранилище/оркестрация по измеренной потребности | Та же семантика KPI и сверки; цена эксплуатации и свежесть приняты командой |

Узкие места измерять: p95 времени типовых запросов при ожидаемом числе пользователей,
длительность сборки относительно окна обновления, CPU/IO/temp spill, блокировки,
размер и темп роста таблиц/индексов, задержка данных, время восстановления из backup.
Замеры и планы сохранять до и после оптимизаций; один медленный JOIN не доказывает
ограничение PostgreSQL.

Предлагаемые измеримые триггеры **для согласования**, не пределы технологии:
если p95 ключевых запросов >3 с при 10 одновременных сессиях в трёх сопоставимых
прогонах после исправления SQL/индексов — оценить материализацию/реплику;
если сборка занимает >50% принятого окна обновления в трёх запусках — оценить
инкремент; если фактическое восстановление превышает согласованный RTO — изменить
backup/восстановление. SLA, RTO/RPO и профиль нагрузки сначала утверждаются человеком.
Переезд из PostgreSQL рассматривать, если эти требования остаются нарушены после
измеренных оптимизаций и экономическое сравнение оправдывает дополнительный сервис.

Доступ: раздельные роли загрузки/сборки/чтения, минимум прав на raw, секреты вне Git.
Тексты отзывов и адресные атрибуты показывать лишь при необходимости; для дашборда
достаточны агрегаты. Версионировать контракт и формулы, предусматривать совместимые
изменения и повторную независимую приёмку. Новые источники сначала профилировать.
