## Общие определения

- **Товарная выручка:** сумма `price` позиций доставленных заказов
  (`order_status = 'delivered'`). Доставка `freight_value` считается отдельно.
  Это стоимость проданных товаров в BRL, а не комиссия/доход площадки.
- **Чек заказа:** сумма `price + freight_value` по его позициям.
  Платежи — отдельный источник для сверки: нельзя автоматически заменить
  ими товарную выручку или умножать платёж на число частей рассрочки.
- **Единица товара:** одна исходная строка позиции; отдельного `quantity`
  в раздатке нет. Число исходных строк и единиц поэтому совпадает.
  Если модель объединяет одинаковые товары, количество нужно сохранить;
  число объединённых строк — уже другой показатель.
- **Заказ:** уникальный `order_id`; **покупатель:** `customer_unique_id`.
  Один покупатель может иметь несколько `customer_id` в разных заказах.
- Деньги считаются точно в `numeric`; округление — только итоговое отображение.
  Для доли: `100.0 * числитель / NULLIF(знаменатель, 0)`.

подтвердить при согласовании. Сравнение Q1 и Q5 выполняется на одинаковом
периоде либо сопровождается сверкой заказов за границами периода Q1.

## Что требуется от контракта A и загрузки B

Это требования к данным для аналитики, не указание создавать конкретные таблицы.

| Уровень одной строки | Нужные поля и гарантии |
|---|---|
| Заказ | Уникальный ключ, статус, время оформления, связь с записью покупателя. Заказы без позиций остаются видимыми для проверки. |
| Позиция | Ключ заказа и номер позиции, товар, продавец, цена и доставка; одна исходная единица либо сохранённое количество при объединении. |
| Покупатель заказа | Однозначная связь `customer_id → customer_unique_id`; несколько записей одного человека не размножают заказ. |
| Продавец | Один ключ → одна строка с городом и штатом. |
| Товар / категория | Однозначное отнесение товара к категории, явная unknown-группа; отсутствие перевода не исключает товар и не склеивает разные категории. |

Прямое соединение позиций, платежей и отзывов создаёт произведение строк.
Например, 2 позиции × 2 платежа дают 4 строки и удваивают сумму позиций.
Каждый набор сначала агрегируется до нужного уровня; ответы читают core/mart.

## Что C проверит перед получением результатов

1. Согласовать v1: статусы/период Q1–Q5, смысл строк и единиц Q3, состав чека.
2. Установить судьбу пропусков: неизвестная категория сохраняет выручку;
   неизвестного покупателя нельзя выдавать за одного реального человека.
3. Посчитать отдельно заказы без позиций и позиции с неполными суммами:
   не считать их нулевым чеком и не исключать незаметно. Решение согласовать.
4. Выполнить запросы, сверить контроли и суммы без промежуточного округления.
   При расхождении проверить статусы, уровень агрегации и потери/размножение JOIN.
5. Сохранить реальные ответы в `results/` с командой запуска и версией модели.
   Числовых результатов C на полной модели пока нет.

## Проверка Q1/Q2

Нужна пустая тестовая PostgreSQL-база и `psycopg2` из зависимостей setup:

```bash
python queries/tests/test_q1_q2.py --dsn "$TEST_DATABASE_URL"
```

Тест создаёт структуру A и небольшой пример в транзакции, затем откатывает её.
При наличии схемы core запуск запрещён. Проверяются 24 месяца, пустые месяцы,
отменённый/недоставленный заказ, граница периода, два продавца в заказе,
повторные единицы товара, несколько платежей/отзывов и одинаковая выручка продавцов.
Q1 требует заполненного календаря: отсутствие ETL нельзя выдавать за нулевые продажи.
Реальные запросы — `queries/01_monthly_revenue.sql` и `queries/02_top_sellers.sql`;
это самостоятельные SELECT, подключения к `model/build.sql` не требуют.
