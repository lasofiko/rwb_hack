## Запуск на PostgreSQL 16

Подключение — стандартные `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`
или `.pgpass`; пароль не помещать в команду/отчёт. Запуск из корня worktree D:

```bash
psql -X -v ON_ERROR_STOP=1 -f checks/00_synthetic.sql
psql -X -v ON_ERROR_STOP=1 -f checks/01_raw_baseline.sql
psql -X -v ON_ERROR_STOP=1 -f checks/10_catalog.sql
```

Первый файл работает в отдельной пустой тестовой БД, `01_raw_baseline.sql` требует
только загруженный raw, `10_catalog.sql` требует построенные core/mart.
Все объекты тестов временные, изменения откатываются. `assert_true` считает
ошибкой и FALSE, и NULL; `assert_numeric` сравнивает без допуска и округления.
Неожиданная ошибка завершает `psql` ненулевым кодом. Ожидаемые ошибки самого
assert перехватываются только в отрицательном контроле синтетического файла.

`01_raw_baseline.sql` сверяет восемь таблиц фиксированной поставки: имена колонок
(включая исходные опечатки), типы text и служебный timestamptz, источник файла,
наличие времени загрузки, объёмы из handout, всего 550 759 строк. Это не профиль B
и не постоянное ограничение для будущих поставок. Новый согласованный snapshot
потребует отдельного baseline; нельзя требовать 550 759 строк от любых новых данных.
Совпадение counts не доказывает тождество содержимого — для пересборок нужен snapshot.

## Приёмка после контракта

Для каждой строки ниже D добавляет SQL с реальными именами таблиц/полей.
В обязательных проверках используется `RAISE EXCEPTION`, а не вывод FALSE.

| Инвариант | Независимое доказательство | Зависимость |
|---|---|---|
| PK и зерно | NULL/дубли PK и бизнес-ключей; order_id; позиция order_id + order_item_id; платёж order_id + sequential | Контракт A, DDL |
| FK | Anti-JOIN каждой связи core; оставшиеся сироты из raw учтены в карантине | A/B |
| Баланс 8 источников | Для каждой исходной строки ровно один исход: загрузка либо изоляция с причиной; проверить пересечения и пропуски, не только count | B: lineage и карантин |
| Деньги и JOIN | Независимые суммы raw → core, затем core → mart по одной и той же популяции; отдельно price/freight/payments, без промежуточного round | A/B/C |
| Категории | NULL, нет перевода, сирота продукта — отдельные количества; суммы/строки до и после JOIN сохранены | A/B/C |
| Покупатель | История по customer_unique_id; адрес принадлежит заказу; сравнить числитель/знаменатель повторных | A/C |
| Календарь | Полный диапазон месяцев C; ровно одна строка на месяц, отсутствующий месяц не потерян | C |
| Платежи/отзывы | Заказы с несколькими строками сохраняют количество и суммы; review_id не объявлен единственным ключом без доказательства | A/B |
| NULL и типы | Денежные поля numeric; исходные отсутствующие значения не превращены в 0, даты без выдуманной timezone; причины ошибок типизации | A/B |
| Ответы | Сверка Q1–Q5 ниже и новых вопросов с фактическими SQL/результатами C | Задания, C |

Считать карантин на уровне исходных строк, даже если одна строка имеет несколько
причин. Схема lineage пока не определена: её отсутствие — зависимость к A/B,
а не повод придумать ключ или применить DISTINCT. Полный профиль raw делает B;
D использует его результаты и повторяет только необходимые независимые сверки.

При расхождении сверить популяцию, статус, даты, price/freight, зерно и JOIN;
контрольное значение не вставлять в расчёт. Денежные суммы сравнивать точно;
округлённые средние/доли — только по правилам C, сохраняя исходные компоненты.

По предложению C: Q1 — delivered, sum(price), дата оформления в
`[2016-09-01, 2018-09-01)`; Q2/Q5 — delivered за всю историю; Q3 — среднее
заказных sum(price + freight_value), delivered; Q4 — вся история/все статусы,
customer_unique_id. D отдельно сверит границы Q1 против всей истории Q5,
заказы без позиций/с неполной ценой и явно утверждённую популяцию Q4.
Платёж payment_value не умножается на payment_installments; синтетика содержит
этот отрицательный пример и различие среднего чека и средней строки.

2. Привязать проверки к контракту и явно исключить из `snapshot.sql` только
   подтверждённые технические timestamps core/mart. Сейчас исключений нет.
3. Снять исходный снимок; `snapshot.sql` включает все столбцы raw и читает только
   таблицы/представления трёх схем. Запустить сборку из чистых core/mart,
   обязательные проверки, снять первый снимок; повторить сборку и проверки.

```bash
psql -X -q -v ON_ERROR_STOP=1 --csv -f checks/snapshot.sql -o checks/before.csv
bash scripts/build.sh
bash scripts/check.sh
psql -X -q -v ON_ERROR_STOP=1 --csv -f checks/snapshot.sql -o checks/first.csv

bash scripts/check.sh
psql -X -q -v ON_ERROR_STOP=1 --csv -f checks/snapshot.sql -o checks/second.csv
git diff --no-index --exit-code checks/first.csv checks/second.csv
```

Это будущие команды: `scripts/build.sh`/`check.sh` ещё не существуют; их владелец A.
Перед запуском snapshots убедиться через `10_catalog.sql`, что схемы заполнены.
Сравнить строки raw в before/first/second отдельно; core/mart до первой сборки
могут отличаться/отсутствовать. После двух сборок snapshots должны совпасть
целиком, включая строки raw. Различие требует объяснения, а не удаления колонок.
Файл включает количество и MD5 мультимножества строк: порядок не влияет, дубли
сохраняются. Это удобный детектор изменений, не криптографическое доказательство;
при расхождении сравнить строки по ключам. На большом объёме сортировка хешей
требует ресурсов. Нестабильные view нужно исправить либо явно согласовать сравнение.
