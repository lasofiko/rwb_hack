# rwb_hack — модель маркетплейса Capibara

Решение команды для кейса «Модель маркетплейса: от корзины до выкупа».
Мы строим в PostgreSQL 16 объяснимую модель данных маркетплейса Capibara
(выгрузка Olist) в три слоя `raw → core → mart`, собираем её одной командой
из сырых данных и отвечаем на вопросы аналитиков SQL-запросами к модели.

**Состояние на 28.10.2026, main `5d60a47`:** сборка с нуля за ~20 с, все 6
обязательных проверок проходят, отклонённых строк 0, контрольные цифры Q1–Q5 совпали.

Правила работы команды — [AGENTS.md](AGENTS.md). Журнал использования ИИ по ролям — [docs/ai/](docs/ai/).

## Быстрый старт

```bash
bash scripts/setup.sh    # Docker, PostgreSQL 16, скачивание CSV, загрузка raw — один раз, меньше минуты
bash scripts/build.sh    # core и mart с нуля из raw, одна транзакция, ~20 с
bash scripts/check.sh    # обязательные инварианты и отчёт по аномалиям
```

Ответ на вопрос — обычный SELECT к модели:

```bash
docker compose exec -T postgres psql -X -U hack -d marketplace -f /work/queries/01_monthly_revenue.sql
```

Подключение: `postgresql://hack:hack@localhost:5432/marketplace` (логин и пароль
простые намеренно, база локальная). Локальный psql не нужен: скрипты запускают его
внутри контейнера, репозиторий смонтирован туда как `/work` (только чтение).

Нужны Docker Desktop или Docker Engine с compose и Python 3.10+;
`psycopg2-binary` `setup.sh` поставит сам.

Если что-то не работает:

- **Схем raw/core/mart нет.** База создана раньше, init-скрипты не выполнились:
  `bash scripts/setup.sh --reset`. Это сносит базу целиком и проверкой модели не является.
- **Порт 5432 занят.** Поменять проброс в `docker-compose.yml` на `"5433:5432"`
  и выполнить `bash scripts/setup.sh --reset`.
- **`ModuleNotFoundError: psycopg2`.** `pip install psycopg2-binary`.
- **Веб-клиент.** `docker compose --profile tools up -d`, затем http://localhost:8080.

## Задание и данные

Capibara — маркетплейс из Сан-Паулу. С сентября 2016 по октябрь 2018 он вырос
от сотен заказов в месяц до семи с лишним тысяч. Данные восьми подсистем лежат
как есть, и каждый отчёт аналитики собирают заново. Наша задача — модель, на которую
аналитики смогут опереться: сырые данные не меняем, модель строим в `core`,
ответы считаем только из модели и можем объяснить каждое решение.

Как устроена площадка: продавец размещает карточку товара; покупатель оформляет
заказ, в котором могут быть товары разных продавцов; каждый продавец отгружает свою
часть до крайнего срока; площадка фиксирует передачу в доставку и вручение;
после получения покупатель может оставить отзыв.

Что сдаём: SQL-сборку модели из raw с нуля; запросы и ответы на вопросы;
записку о решениях (до полстраницы); концепцию дашборда; стратегию развития.
Всё это — разделы этого README.

Источник: [Brazilian E-Commerce Public Dataset by Olist](https://github.com/olist/work-at-olist-data),
лицензия CC BY-NC-SA 4.0, идентификаторы обезличены. Раздатка —
[daniilivanovp-droid/hackathon-students](https://github.com/daniilivanovp-droid/hackathon-students),

## Модель

### Слои

| Слой | Что там | Кто читает |
|---|---|---|
| `raw` | 8 таблиц как пришли из CSV, все колонки `text`, служебные `_source_file`, `_loaded_at`. После штатной загрузки не меняется | загрузка и сверки |
| `core` | наша модель: 10 таблиц с настоящими типами, ключами и ограничениями; пересобирается с нуля | запросы, проверки |
| `mart` | витрины для дашборда; сейчас пустая — ответы Q1–Q5 считаются запросами к core | дашборд |

### Таблицы core

Главный вопрос к каждой таблице — что такое одна её строка (зерно).
Колонки и типы — в [model/10_ddl.sql](model/10_ddl.sql).

| Таблица | Одна строка | PK | FK | Строк | Источник |
|---|---|---|---|---:|---|
| `customers` | покупатель-человек | `customer_unique_id` | — | 96 096 | distinct из `raw.customers` |
| `orders` | заказ + адрес этого заказа | `order_id`; `customer_id` UNIQUE | `customer_unique_id` | 99 441 | `raw.orders` + `raw.customers` по `customer_id` |
| `order_items` | одна единица товара одного продавца в заказе | `(order_id, order_item_id)` | `order_id`, `product_id`, `seller_id` | 112 650 | `raw.order_items` |
| `order_payments` | платёж заказа | `(order_id, payment_sequential)` | `order_id` | 103 886 | `raw.order_payments` |
| `order_reviews` | отзыв о заказе | `(review_id, order_id)` | `order_id` | 99 224 | `raw.order_reviews` |
| `products` | карточка товара | `product_id` | `product_category_name` (NULL = не указана) | 32 951 | `raw.products` |
| `sellers` | продавец | `seller_id` | — | 3 095 | `raw.sellers` |
| `categories` | категория (португальское имя) и перевод, если есть | `product_category_name` | — | 73 | перевод + категории товаров без перевода |
| `calendar` | день | `day` | — | 821 | 2016-09-01 … 2018-11-30, 27 месяцев |
| `etl_rejects` | строка raw, не попавшая в core, с причиной | — | — | 0 | все raw |

Позиции, платежи и отзывы связаны только с заказом, между собой — никогда.
У заказа может не быть позиций, платежа или отзыва: дочерние наборы необязательны.

### Сборка

`bash scripts/build.sh` выполняет [model/build.sql](model/build.sql) одной транзакцией:

1. проверяет, что все 8 таблиц raw не пусты;
2. `DROP/CREATE SCHEMA core, mart` — пересобираются только производные схемы, raw не трогаем;
3. `10_ddl.sql` — таблицы, ключи, ограничения, индексы;
4. загрузка raw → core строго в этом порядке:
   `20_1_dims.sql` (разбор raw; customers, sellers, categories, products) →
   `20_2_orders.sql` → `20_3_order_children.sql` (items, payments, reviews, rejects) →
   `20_4_calendar.sql` (календарь и проверка баланса: ошибка, если не сходится);
5. витрины mart (пока нет).

Ошибка в любом файле откатывает всю сборку: core и mart остаются как были,
скрипт возвращает ненулевой код. Повторный запуск на том же raw даёт тот же результат.

### Правила для SQL-файлов модели

- Без `BEGIN/COMMIT`: транзакцией управляют `build.sql` и `check.sh`.
- Имена всегда со схемой (`core.orders`, `raw.orders`), явные списки колонок в `INSERT`.
- Тексты (id, статусы, города, отзывы) переносятся как в источнике: без `trim`, `lower`, `DISTINCT`.
- Типизированные колонки: `NULLIF(x, '')`, проверка `pg_input_is_valid(x, '<тип>')`, приведение.
  Деньги — `numeric` без typmod (без молчаливого округления), время — `timestamp` без часового пояса.
- NULL в core значит «неизвестно». Ноль, `unknown`, единица рассрочки вместо NULL или 0 не подставляются.

### Плохие строки

Строка raw, которая не может попасть в core, кладётся в `core.etl_rejects`,
и сборка продолжается. Так баланс `raw = core + rejects` доказывает, что ничего не пропало.

| reason | Когда |
|---|---|
| `null_key:<колонка>` | пустая колонка ключа |
| `duplicate_key` | у ключа несколько строк — отклоняются **все**, «правильную» не выбираем |
| `bad_type:<колонка>` | `pg_input_is_valid` = false |
| `null_required:<колонка>` | пусто в колонке `NOT NULL` |
| `invalid_value:<колонка>` | нарушает `CHECK` (оценка вне 1..5, отрицательные деньги, рассрочка < 0) или у обещанной даты есть время |
| `orphan:<таблица>` | нет родителя в core, в том числе потому, что отклонён родитель; для `raw.customers` — запись не связана ни с одним принятым заказом |

В `reason` — первая найденная причина, `source_key` — ключ источника через `|`,
`payload` — исходная строка целиком (`to_jsonb`). Сборка падает только на ошибке SQL
или нарушении ограничения core: это баг загрузки, а не данных.

### Решения по модели

- **Покупатель — `customer_unique_id`.** `customer_id` выдаётся на каждый заказ:
  99 441 id на 96 096 людей, у одного человека до 17. `customer_id` хранится в заказе.
- **Адрес — в заказе**, а не последний адрес человека: 39 человек заказывали в разные штаты.
- **Ключ отзыва `(review_id, order_id)`.** 789 значений `review_id` повторяются в разных заказах.
- **Категории.** Товар без категории (610) остаётся NULL; строки `unknown` в core нет,
  подпись даёт ответ. Две категории без перевода (`pc_gamer`,
  `portateis_cozinha_e_preparadores_de_alimentos`) есть в `categories` с NULL-переводом.
- **ZIP — как в источнике** (4–5 цифр), без дополнения нулём.
- **Тексты отзывов — байт в байт**, включая пробелы по краям и пробельные сообщения.
- **Даты — без коррекции**, включая аномалии порядка этапов.
- **Платежи** — рассрочка `0` и тип `not_defined` как есть, нулевые платежи допустимы.
- `order_estimated_delivery_date` — `date`: время в источнике всегда 00:00:00, иначе строка отклоняется.
- Опечатка `lenght` исправлена в core: `product_name_length`, `product_description_length`.

## Данные: профиль и аномалии

Профиль восьми таблиц снят на свежей загрузке раздатки (PostgreSQL 16.15).
У всех кандидатов ключей нет NULL, пустых значений и дублей; полных дублей строк нет;
все непустые значения приводятся к целевым типам; сирот по шести связям нет.
SQL и агрегаты — в [profiling/](profiling/).

Аномалии сохранены как есть и учтены явно:

| Что | Сколько | Что делаем |

## Метрики и ответы Q1–Q5

Определения:

- **Товарная выручка** — сумма `price` позиций доставленных заказов
  (`order_status = 'delivered'`), в BRL. Доставка `freight_value` — отдельные деньги.
  Это стоимость проданных товаров, а не доход площадки.
- **Чек заказа** — сумма `price + freight_value` по его позициям. Платежи — отдельный
  источник для сверки: ими нельзя подменять выручку.
- **Единица товара** — одна строка позиции; отдельного количества в данных нет.
- **Заказ** — `order_id`, **покупатель** — `customer_unique_id`.
- Деньги считаются точно в `numeric`, округление — только при выводе.
  Доля — `100.0 * числитель / NULLIF(знаменатель, 0)`.
- Позиции, платежи и отзывы сначала сворачиваются до заказа, потом соединяются:
  2 позиции × 2 платежа дали бы 4 строки и удвоили сумму.

| # | Вопрос | Как считаем | Ответ | Контроль |
|---|---|---|---|---|
| Q1 | Выручка и число заказов по месяцам, сентябрь 2016 — август 2018 | delivered; месяц по `order_purchase_timestamp`; сумма на заказ, потом по месяцам; календарь `[2016-09-01, 2018-09-01)` слева, пустой месяц = 0 | 24 месяца, 2016-11 = 0, итого **13 221 498.11** | 24 строки, одна нулевая, 13 221 498.11 ✓ |
| Q2 | Топ-10 продавцов по выручке с городом и штатом | только позиции продавца в доставленных заказах; заказы `COUNT(DISTINCT order_id)`; город и штат из `sellers`; при равенстве — по ключу продавца | лидер `4869f7a5…`, guariba, SP: 1 124 заказа, 1 148 единиц, **226 987.93** | 226 987.93 ✓ |
| Q3 | Средний чек | одна строка на каждый из 96 478 доставленных заказов, потом простое среднее | **159.88**; строк и единиц на заказ 1.142; заказов без позиций 0 | 159.88 ✓ |
| Q4 | Покупатели и повторные покупки | по `customer_unique_id`, вся история, все статусы — повторное оформление заказа | **96 096**, вернулись 2 997, **3,12%** | 96 096, 3,12% ✓ |
| Q5 | Выручка по категориям с долей | delivered, вся история; группа по исходному ключу категории; подпись — перевод, иначе исходное имя, иначе `unknown` | **74** группы, лидер health_beauty **1 233 131.72**, сумма 13 221 498.11 | 74, 1 233 131.72, 13 221 498.11 ✓ |

Ловушки, посчитанные на нашей модели:

- Q1: без календаря — 23 строки; без фильтра статуса — 13 591 498.70;
  позиции × платежи до агрегации — 13 813 828.71.
- Q2: в 1 278 заказах несколько продавцов; если приписать продавцу всю сумму заказа,
  у лидера выйдет 230 466.81.
- Q3: среднее по позициям вместо заказов — 123.75 (цена товара) или 139.97 (позиция с доставкой).
- Q4: по `customer_id` — 99 441 покупатель и ни одного повторного. Только по доставленным — 93 358 и 3,00%.
- Q5: INNER JOIN со справочником переводов теряет unknown (170 726.63) и две категории

## Записка о решениях

| Выбор | Альтернатива | Причина |
|---|---|---|
| Неизменяемый raw → типизированный core → mart нужного зерна | чистить raw на месте | аудит, объяснение потерь, воспроизводимость |
| Отдельные факты позиций, платежей и отзывов; JOIN после агрегации | одна плоская таблица | связи 1:N умножают деньги и строки |
| Покупатель по `customer_unique_id`, адрес в контексте заказа | `customer_id`, последний адрес | повторные покупки и достоверная история |
| `numeric`; NULL в core, `unknown` в ответе; карантин с причиной | `float`, NULL → 0, молчаливый INNER JOIN | точные суммы и объяснимый баланс строк |
| Календарная ось; доли, средние и уникальные пересчитываются | только месяцы с фактами; сумма готовых KPI | пустой месяц и корректные итоги |
| PostgreSQL 16 и SQL-сборка с нуля одной транзакцией | оркестратор или облако в MVP | меньше зависимостей, проще проверить и защитить |

Даты и деньги источника не корректируем; тексты сохраняем точно. Выручка — `price`
доставленных заказов, чек — `price + freight_value`, повторные — все статусы, BRL.

## Концепция дашборда

**Пользователь** — руководитель маркетплейса. **Решения:** где меняется объём продаж,
какие продавцы и категории дают вклад, возвращаются ли покупатели. На каждом экране
видны период, поле даты, статусы, валюта BRL, дата загрузки и предупреждение о неполных данных.

| Блок / решение | Формула | Зерно и поля |
|---|---|---|
| Динамика / найти спад | `sum(price)` позиций delivered; доставка отдельно; период Q1 | `calendar(day, month_start)`, `orders(order_id, order_purchase_timestamp, order_status)`, `order_items(order_id, price, freight_value)` |
| Продавцы / вклад | сумма только позиций продавца; доля = продавец / все в том же срезе | `order_items(order_id, order_item_id, seller_id, price)`, `sellers(seller_id, seller_city, seller_state)` |
| Категории / ассортимент | сумма позиций по категории, включая unknown; доставка отдельно | `order_items(product_id, price)`, `products(product_id, product_category_name)`, `categories` |
| Средний чек / размер покупки | `avg` заказного `sum(price + freight_value)`, delivered | `order_items` до `order_id`, затем `orders`; `order_payments` — отдельная сверка |
| Повторные / удержание | 100 × покупатели с ≥ 2 заказами / покупатели с ≥ 1 заказом; вся история, все статусы | `orders(order_id, customer_unique_id)`, `customers`; адрес — `orders.customer_state` |
| Качество / доверие | отклонённые строки по источнику и причине; unknown; заказы без нужной даты или цены | `etl_rejects(source_table, source_key, reason, payload)`, `products`, `orders` |

Срезы: период, статус, продавец, категория, штат адреса заказа. Географию продавца
и адрес покупателя не смешиваем. Период фильтруется по дате заказа, не по дате загрузки;
месяцы без фактов показываются через календарь с нулём. Отсутствие цены не превращается
в нулевую цену. Платёж и чек могут расходиться — это разные показатели.

**Неаддитивность.** Сумма позиций складывается по непересекающимся категориям и продавцам.
Число заказов по категориям, уникальные покупатели (один человек заказывал в разные штаты),
доля повторных, средний чек и доли не складываются: их пересчитываем из числителя
и знаменателя после фильтра. Платёж всего заказа нельзя делить между продавцами без
отдельного правила. Отзывы и платежи агрегируются до соединения с заказом.

## Стратегия развития

MVP — PostgreSQL 16, неизменяемый raw, core и витрины; текущий объём 550 759 строк,
сборка ~20 с. Сначала корректность и повторяемость, потом скорость.

| Этап | Изменение и польза | Приёмка / риск |
|---|---|---|
| 1. Повторяемый batch | реестр загрузок: batch_id, источник, хеш файла, время; lineage и карантин с причинами | повторная загрузка не удваивает строки, баланс сходится; риск — нестабильный ключ источника |
| 2. История | события статусов заказа; история атрибутов товара и продавца с `valid_from/valid_to`; адрес заказа сохраняется | нет пересечений интервалов, корректный as-of JOIN; прошлые переходы из нынешнего снимка не восстановить — не выдумываем |
| 3. Новые сущности | возвраты и отмены на уровне позиций, возвраты платежей, комиссии, логистика отдельными фактами | выручка, оборот, оплачено и возврат различаются; риск двойного учёта компенсаций |
| 4. Рост нагрузки | индексы по измеренным планам, ANALYZE, материализация; инкрементальная загрузка с окном поздних данных; партиции, если помогают | инкремент сверяется с полной пересборкой; `EXPLAIN (ANALYZE, BUFFERS)`; риск пропуска поздних исправлений |
| 5. Расширение | реплика для аналитики, затем отдельное хранилище или оркестрация по измеренной потребности | та же семантика KPI и сверки; цена эксплуатации принята командой |

Узкие места измеряем: p95 типовых запросов, длительность сборки относительно окна
обновления, CPU/IO/temp spill, блокировки, рост таблиц и индексов, задержка данных,
время восстановления. Триггеры для согласования, а не пределы PostgreSQL: p95 ключевых
запросов > 3 с при 10 сессиях в трёх прогонах после правки SQL и индексов — оценить
материализацию или реплику; сборка > 50% окна обновления в трёх запусках — оценить
инкремент; восстановление дольше согласованного RTO — менять backup. Уход с PostgreSQL —
только если требования нарушены после измеренных оптимизаций и это оправдано экономически.

Доступ: раздельные роли загрузки, сборки и чтения, минимум прав на raw, секреты вне git.
Тексты отзывов и адреса — только при необходимости, дашборду хватает агрегатов.
Контракт и формулы версионируем, новые источники сначала профилируем.

## Защита за 3 минуты

1. **Задача.** Объяснимо отвечать на вопросы через `raw → core → mart`: raw хранит
   источник, core задаёт типы, ключи и судьбу каждой строки, mart — удобное зерно для метрик.
2. **Главное решение.** У заказа, позиции, платежа и отзыва разное зерно; соединяем
   после агрегации, поэтому суммы не умножаются.
3. **Покупатель** — `customer_unique_id`, адрес — в контексте заказа.
4. **Доказательство.** Баланс и построчная сверка raw/core, чистая и повторная сборка
   с одинаковым результатом, неизменный raw, совпадение Q1–Q5.
5. **Ограничения и рост.** Неизвестные категории и плохие строки учитываем явно;
   историю статусов нынешний снимок не хранит; развитие — по измерениям.

Каждый в команде объясняет зерно, ключи, соединения и одну реальную аномалию
из таблицы выше.

## Профилирование raw

SQL профиля работает в одном repeatable-read снимке, создаёт только временные объекты,
заканчивается `ROLLBACK` и выводит JSONL с агрегатами без текстов отзывов:

```sh
psql "$DATABASE_URL" -X -q -v ON_ERROR_STOP=1 -f profiling/01_raw_profile.sql > profiling/raw-profile.jsonl
```

| Файл | Что |
|---|---|
| `01_raw_profile.sql` → `raw-profile.jsonl` | строки, NULL и пустые, пробелы, приводимость типов, ключи, дубли, связи, кратность, статусы, деньги, хронология |
| `02_followup.sql` → `followup.jsonl` | точечные уточнения после профиля |
| `03_reconciliation.sql` → `reconciliation.jsonl` | разложение разницы платежей и позиций по заказам и статусам |
| `04_verify_etl.sql` → `etl-verification.jsonl` | ожидаемые числа после загрузки, сохранность текста, raw и денег, подписи таблиц core |
| `05_etl_fixture.sql` → `etl-fixture.jsonl` | загрузка на синтетике: типы, все коды отказов, тексты, адреса, календарь |
| `06_contract_facts.sql` → `contract-facts.jsonl` | дополнительные факты для модели |
| `source-manifest.json` | URL, размер и SHA-256 каждого CSV |

PowerShell-обёртки (`bootstrap.ps1`, `run.ps1`, `verify-etl.ps1`, `test-etl.ps1` и др.)
поднимают отдельную базу `marketplace_b` на порту 55432 и не трогают общую.
