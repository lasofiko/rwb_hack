# Профиль raw (роль B)

Изолированный worktree: `rwb_hack_b`, ветка `b/raw-profile-etl`.
Раздатка: `hackathon-students`, commit `3da32d149bfa14dca3fdb0c5863d0771c38efbfc`.
DDL взят из `scripts/init/02_raw_ddl.sql` без изменения структуры.
CSV скачиваются по адресам штатного `scripts/download_data.sh` раздатки;
`source-manifest.json` фиксирует URL, размер и SHA-256 каждого файла.
Это данные из источника раздатки, а не доказательство идентичности иной БД команды.

Из корня worktree в PowerShell:

```powershell
./profiling/bootstrap.ps1 -HandoutRoot ../hackathon-students
./profiling/run.ps1
```

Bootstrap создаёт отдельный Compose project `rwb-b`, volume `rwb-b_pgdata`,
БД `marketplace_b`, порт `127.0.0.1:55432`, пользователь/пароль `hack`.
Повторная инициализация существующего raw запрещена и завершается ошибкой.
Скачанные CSV и SQL загрузки находятся в игнорируемом `profiling/local/`.
Не запускать `down -v` для проверки модели.

Профиль можно выполнить против любой уже загруженной БД PostgreSQL 16+:

```sh
psql "$DATABASE_URL" -X -q -v ON_ERROR_STOP=1 -f profiling/01_raw_profile.sql > profiling/raw-profile.jsonl
```

SQL работает в одном repeatable-read snapshot, создаёт только временные объекты,
завершает транзакцию ROLLBACK, не меняет raw/core/mart. Нужны SELECT на восьми
raw-таблицах и право TEMP в БД. Вывод — JSONL с агрегатами без текстов отзывов.
Временные таблицы требуют обычной транзакции, а не `READ ONLY`.
`run.ps1` сохраняет JSONL только после успешного psql и проверки JSON;
при ошибке прежний результат остаётся на месте. Полное профилирование достаточно
выполнить один раз для конкретного снимка; при изменении входа нужен новый профиль.

Проверяются строки/источники загрузки, все пользовательские колонки (NULL,
пустые значения, пробелы, distinct, возможность приведения, диапазоны), ключи,
полные дубли без metadata, связи, кратность дочерних сущностей, статусы,
оценки, идентичность покупателей, суммы денег и аномалии хронологии.
Колонки `_source_file`/`_loaded_at` не участвуют в бизнес-дублях.
Типы пока кандидаты для A: окончательные имена/типы/NULL/PK/FK задаёт контракт.
Составной ключ отзывов `(review_id, order_id)` проверяется как кандидат, а не
навязывается модели; отдельная проверка показывает повторяемость `review_id`.

Точечные уточнения после профиля (только если профиль подтвердил корректность
numeric/integer): `./profiling/followup.ps1` или
`psql "$DATABASE_URL" -X -q -v ON_ERROR_STOP=1 -f profiling/02_followup.sql`.
Результат — `followup.jsonl`; запрос не повторяет полный профиль.

Разложение разницы payment−(price+freight) по заказам и статусам:
`./profiling/reconcile.ps1`; SQL `03_reconciliation.sql`, результат
`reconciliation.jsonl`. Запускать после успешного профиля типов numeric.
Он сохраняет отсутствие дочернего набора как NULL и агрегирует каждый набор
до заказа перед JOIN; это точечная сверка источников, а не повторный полный профиль.
