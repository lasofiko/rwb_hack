# Концепция дашборда

Статус: фактический интерфейс четырёх файлов B, main 2c4017f. UI не требуется.
Пять ответов C независимо воспроизведены D на полном снимке; повторяемость D
и штатная интеграция A пока не подтверждены. Формулы — текущая реализация C.

Пользователь — руководитель маркетплейса. Решения: где меняется объём продаж,
какие продавцы/категории дают вклад, насколько возвращаются покупатели.
На каждом экране видны период, временное поле, статусы, валюта, дата загрузки
и предупреждение о неполных данных. В предложении C валюта — BRL.

| Блок / решение | Формула для согласования с C | Зерно / нужные поля контракта |
|---|---|---|
| Динамика / найти спад | sum(price) позиций delivered; freight_value отдельно; период Q1: [2016-09-01, 2018-09-01) | core.calendar(day, month_start); core.orders(order_id, order_purchase_timestamp, order_status); core.order_items(order_id, price, freight_value) |
| Продавцы / вклад | Сумма стоимости только позиций продавца; доля = сумма продавца / сумма всех в явно указанном срезе | core.order_items: (order_id, order_item_id), seller_id, price; core.sellers(seller_id, seller_city, seller_state) |
| Категории / ассортимент | Сумма позиций по категории, включая unknown; доставка отдельно | core.order_items(product_id, price); core.products(product_id, product_category_name); core.categories(product_category_name, product_category_name_english) |
| Средний чек / размер покупки | avg(заказной sum(price + freight_value)), delivered; при наличии доставленного без позиций Q3 возвращает NULL средних и количество таких заказов | core.order_items агрегируется до order_id, затем core.orders; core.order_payments — отдельная сверка |
| Повторные / удержание | 100 × покупатели с ≥2 разными заказами / покупатели с ≥1 заказом; C предлагает всю историю и все статусы | core.orders(order_id, customer_unique_id); core.customers(customer_unique_id); адрес core.orders.customer_state |
| Качество / доверие | Изолированные строки по источнику/причине; unknown; заказы без нужной даты/цены | core.etl_rejects(source_table, source_key, reason, payload); core.products; core.orders; counts |

Период фильтруется по согласованной дате заказа, не по дате загрузки.
Месяцы без фактов показываются через календарь с 0 заказов. Отсутствие цены
не превращается в нулевую цену; рядом нужна полнота суммы. Категория без перевода
сохраняется с исходным названием и отметкой, отсутствующая категория — unknown.
По профилю B платёж и чек могут расходиться; их показывают разными показателями,
а не подменяют один другим. Проценты Q5 округляются только при отображении,
поэтому сумма показанных долей может отличаться от 100%.

Срезы: период, статус, продавец, категория, штат адреса заказа. Географию продавца
и адрес покупателя не смешивать. Фильтр по продавцу/категории меняет популяцию
заказов: заказ учитывается один раз в чеке и повторных, даже если содержит
несколько подходящих позиций. Как именно фильтруется сумма чека, согласует C;
до этого смешанный KPI не публиковать. Базовый Q4 C не зависит от фильтра продаж
delivered: подпись «повторное оформление за всю историю, все статусы».
Любое окно или иной статус для этого блока — отдельная метрика с явной подписью.

Сумма позиций аддитивна по взаимоисключающим категориям/продавцам. Платёж всего
заказа нельзя распределять между продавцами без отдельного правила. Число заказов
по категориям, уникальные покупатели и повторные неаддитивны; средние и доли
пересчитываются из исходных числителей/знаменателей после фильтра. Отзывы и платежи
агрегируются до соединения с заказом. Показатели качества не прятать в бизнес-KPI.

Приёмка: календарь полный; сумма категорий с unknown совпадает с общей на одной
популяции; итоговые доли пересчитаны; несколько платежей/отзывов не меняют выручку;
все графики объясняются сохранёнными SQL C. Проверки D первого полного состояния прошли; финальную штатную сборку ещё нужно повторить.
